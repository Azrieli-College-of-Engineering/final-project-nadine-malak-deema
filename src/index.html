🎓 Web Security Final Project

DOM-XSS & CSP
Experiment Hub

Four fully isolated, independently testable environments demonstrating the progression from a fully vulnerable application to a securely implemented one. Each version isolates a single security configuration.

Version 01 / 04
❌ No CSP
No Content-Security-Policy header set
The baseline vulnerable state. No policy restricts script execution. All payloads execute freely. Demonstrates the raw impact of DOM-XSS without any mitigation.
Inline scripts: ALLOWED
Event handlers: ALLOWED
Token theft: SUCCEEDS
HTML injection: SUCCEEDS
FULLY VULNERABLE Open Version 1 →
Version 02 / 04
⚠ Weak CSP
script-src 'self' 'unsafe-inline'
CSP header is present but misconfigured with 'unsafe-inline'. This explicitly permits all inline scripts and event handlers — making the CSP completely ineffective against XSS. Creates a dangerous false sense of security.
Inline scripts: STILL ALLOWED
Event handlers: STILL ALLOWED
Token theft: STILL SUCCEEDS
False security: HIGH RISK
FALSE SENSE OF SECURITY Open Version 2 →
Version 03 / 04
🛡 Strict Nonce CSP
script-src 'self' 'nonce-xSec2024ProjectNonce'
A properly configured nonce-based CSP. Script execution from injected payloads is blocked — you'll see CSP violations in DevTools. However, HTML injection still succeeds because the root innerHTML vulnerability is not fixed.
Inline scripts: BLOCKED ✓
Event handlers: BLOCKED ✓
JS token theft: BLOCKED ✓
HTML injection: STILL WORKS ✗
PARTIAL MITIGATION Open Version 3 →
Version 04 / 04
✅ Secure Code
textContent replaces innerHTML + Strict CSP
The root vulnerability is eliminated. textContent treats all input as plain text — no HTML is ever parsed. Combined with strict nonce CSP, this provides complete defense-in-depth. All payloads are displayed as harmless literal text.
Inline scripts: BLOCKED ✓
Event handlers: BLOCKED ✓
Token theft: IMPOSSIBLE ✓
HTML injection: IMPOSSIBLE ✓
FULLY SECURE ✓ Open Version 4 →

🚀 How to Test Each Version

1
Login first — Go to login.html, enter student / 1234 to create a session token in localStorage.
2
Open a version — Click any card above, or navigate directly to the file.
3
Open DevTools — Press F12 → Console tab. CSP violations appear here as red errors on V3/V4.
4
Try the payloads — Use the pre-built payload buttons inside each version, or type your own in the inject field.
5
Test via URL — Directly append ?report=<img src=x onerror=stealToken()> to the URL of each version to simulate the real attack vector.
6
Compare results — Observe how the same payload behaves differently across all 4 versions. This is the core experiment.
